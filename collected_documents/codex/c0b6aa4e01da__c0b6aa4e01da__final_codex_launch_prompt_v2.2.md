# Launch CRE Codex Project OS v2.2

Initialize and operate the CRE Tip Sheet / CRE Foundry project from the
repository-owned Project OS.

The durable objective is defined in `kernel/MISSION.md`: build the strongest
defensible system that issues exactly 10 feasible physical business locations
per standardized representative route-day for first-touch CRE prospecting,
maximizing incremental F9 bookings and risk-adjusted expected net commercial
value, or returns `ABSTAIN_NO_VALID_TEN`.

Do not treat this prompt as the knowledge base. The repository files, task
graph, evaluators, artifacts, and state are the system of record.

## Start

1. Locate the launch kernel, reference vault, and actual project repository.
2. Read `README_START_HERE.md` and `AGENTS.md`.
3. Run:
   - `python scripts/validate_os.py`
   - `python scripts/validate_research_readiness.py`
   - `python scripts/run_level10_campaign.py`
   - `python scripts/probe_codex_capabilities.py`
   - `python scripts/select_next_task.py`
   - `python scripts/compile_task_context.py`
4. Read the generated current-task packet.
5. Execute `BOOTSTRAP-001`.

## Operating contract

Follow `control/WORKFLOW.md`.

Work depth-first. After repository truth and evaluator foundations, establish
the earliest thin end-to-end shadow vertical slice before expanding every
subsystem horizontally.

For each task:

- load only the compiled task context;
- classify relevant expertise domains;
- use independent read-heavy agents and one writer per worktree;
- define or verify the evaluator before material implementation;
- use Best-of-N for consequential choices;
- preserve hard invariants while challenging implementation preferences;
- implement, test, independently sweep, repair/combine/revert, integrate, and
  checkpoint;
- update claims, decisions, artifacts, gates, state, and the next task.

Continue while authorized positive-value work exists. A turn or context window
ending is a checkpoint, not project completion. Resume from state and artifacts.

## Execution mode

Detect the environment and use `control/EXECUTION_MODES.md`.

- Interactive/Goal mode: execute as much bounded work as the durable thread and
  approvals permit, then checkpoint.
- Headless mode: use only capabilities confirmed by the probe; preserve
  session/thread identifiers and validate structured task output.
- Tracker-orchestrated mode: use the issue tracker as the control plane, one
  isolated workspace per issue, bounded concurrency, retries, reconciliation,
  and repository-owned workflow policy.
